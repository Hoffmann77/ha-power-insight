## Why this case exists

[Group captivity](./group-captivity.mdx) is about a *group of sinks* that
together need a set of sources. This case is its mirror image: *one sink* that
needs a group of sources — the two strings of one array — without needing
either string in particular.

That is exactly what a solver reasoning one source at a time cannot see. Ask
"what must the plug take from `pv1a`?" and the answer is nothing, because `pv1b`
could cover it; ask the same of `pv1b` and the answer is again nothing. So
nothing is set aside for the plug on either string, even though it needs 400 W
of the pair.

Meanwhile the export *does* have something set aside: `pv2` may feed nothing
else, so all 200 W of it must go to the export in any valid allocation. The
engine used to offer the export a share of all three sources, find the offers
added up to more than its 1800 W, and scale every offer down by the same factor
— including the 200 W it had to take from `pv2`. It took 180 W, and the 20 W of
`pv2` it left behind could go nowhere but the plug, which may not use it. The
plug was shown drawing 20 W from `pv2` and a restriction deficit was reported
for a configuration that had nothing wrong with it.

Register the same array as one device and none of this happens: the plug then
needs all 400 W from that one device, which is reserved for it up front. A
house should not get different numbers for how its inverter is registered.

The fix is that offers are still scaled down together — which keeps each sink's
split in proportion to what its sources have left — but never below what a
source *must* carry in every valid allocation.

This needs no base load to go wrong only because with one, the slack hides the
mistake. In the snapshot above every watt is spoken for, so there is nowhere
for a misplaced watt to go.
