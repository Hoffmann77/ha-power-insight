# Reference cases

Some of what the engine reports is plain arithmetic. Some of it is a **modelling
choice** — a place where more than one answer is defensible, and Power Insight
picks one.

Those choices are what this section is for. Each **reference case** is a small,
deliberately-chosen wiring whose every value is published here, so you can
disagree with the *model* without reading a line of Python.

The values on these pages are generated from the engine, so they are always a
true record of what it currently computes. Asserting them back against the
engine in CI — so that a change to the code which contradicts these pages fails
the build — is the next step, and not yet in place.

## The cases

The corpus is a **ladder**. It starts at a house with one meter in it and adds
exactly one device — or flips exactly one configuration flag — per rung, so a
diagram is always the previous diagram plus one thing. Read it in order and
nothing arrives unexplained. Two rules keep it from sprawling:

- A case earns its place only if it settles a decision **no lower rung can
  express**. Where a decision *is* expressible lower down it belongs lower down,
  because a value derived by hand across three devices takes a minute and the
  same rule across six takes an afternoon.
- A snapshot earns its place only if it moves a published value that no other
  snapshot of its case moves.

The last two cases break the one-thing-at-a-time growth deliberately. They are
**specialists**: Hall's condition quantifies over *subsets* of sinks and cannot
be shown with fewer than two sources and two restricted sinks, and unequal
export permissions mean nothing without two dischargers that differ. Neither is
the first home of any decision — they are there to check that the rules below
them still hold when they all apply at once.

## How to read a diagram

Devices sit on the side their **reading's sign** puts them on this snapshot —
sources on the left, sinks on the right. That is not decoration: a grid that is
importing is a *source*, and the same grid exporting is a *restricted sink*. The
sides move as you step through the snapshots.

Edge width is proportional to watts, and each edge takes the colour of the
source it comes from. The dashed circle is the **home base load**: everything
consumed without a sensor on it. It has no device behind it, competes for power
like any other sink, and is derived rather than measured.

Click any device to focus it. Everything it does not exchange power with fades
back, and a grey dashed line appears for any source it is *allowed* to use but
currently is not — which is usually the most interesting thing on the page.
Click it again, or anywhere else on the diagram, to step back out.

### The four layers

The engine computes in layers, and the tab row steps through them. Each one
re-labels the same picture and lists every value the engine published for that
snapshot underneath, with the exact fraction beside the figure.

| Layer | The question it answers |
| --- | --- |
| **Totals** | What did each meter read, and what do those readings add up to? |
| **Provenance** | For each sink, where did its power come from? |
| **Channels** | What was the gross power *used for* — export, self-consumption, charging, standby? |
| **Money** | What did that cost, what did it avoid, and what is each source priced at? |

Any row in the value table with a caret next to it will explain itself: the
engine's own definition of the property, and the formula where one has been
checked against a real value.

## Certification

A dot next to a value says where that value came from. An open dot means
**unverified** — generated by the engine, not yet checked by a human. A filled
dot means **verified** — derived by hand, independently, and it agreed with the
engine.

Certification is deliberately slow: values are worked out on paper, blind,
without the engine's answer visible, a few at a time. Everything is unverified
today. That is honest rather than embarrassing — you can see exactly how far the
hand-checking has got, and a value nobody has certified is one worth arguing
with.

## Coverage

The ladder is an ordering, and an ordering is only worth anything if you can see
what it achieved. This table is generated with the cases, so it cannot drift
from them.

The column that matters is **settled by**. It is not a count of appearances:
almost every property has *some* value on rung 0, because a one-meter house
still has a gross power and a cost of energy, so "where does it first show up"
says nothing. The rungs listed are the ones that each published a value for that
property which no earlier rung had. A property settled by one rung is pinned by
a single wiring and merely repeated everywhere above it. A property settled by
eight is one the corpus is genuinely working.

## Open questions

A snapshot carrying an **open question** is one where the engine produces an
answer but which answer is *right* has not been settled. They are marked with an
amber dot in the snapshot cards, and spelled out on the case page. If you have a
view, the issue tracker is the place for it — that is exactly what publishing
these cases is meant to invite.
